## 核实的机制（全部有源码 + 实测双重依据）

- **事务绑在「连接」上，不是绑在「会话」上。** 判据是 `Statement.ConnPool`：
  `BeginTransaction` 把它换成 `*sql.Tx`，`CommitOrRollbackTransaction` 换回 `*sql.DB`。
  全局 `db` 的 `ConnPool` 始终是连接池 → 钩子里的 `db.Xxx()` 另取一条连接、语句级自动提交。
- **实测铁证**：钩子里 `SELECT CONNECTION_ID()` —— 用 `tx` 时 16（= 事务那条），用 `db` 时 17。
  结果：用 `db` 时用户回滚了、计数器留在 1 → 这就是「数据不一致」。
- **钩子的 `tx` 来自** `callbacks/callmethod.go`：`db.Session(&gorm.Session{NewDB: true})`。
  `NewDB: true` → `clone = 1` → `getInstance()` 新建空 Statement，但 `ConnPool: db.Statement.ConnPool`
  → 「干净 + 同事务」两件事一次到位。
- **因为 `clone = 1`，批量插入时钩子里的 `tx.Model(...).Where(...)` 不会跨元素累积条件**（实测：三条各更新自己的计数器）。
  但用户自己攒的链式对象是 `clone = 0`，`getInstance` 返回自身 → 复用必污染。
- **`clone` 三态**：`1` 全新空 Statement / `2` 带条件克隆（`Session(&gorm.Session{})`）/ `0` 返回自身。
  安全复用模板用 `.Session(&gorm.Session{})`；清空条件才用 `NewDB: true`。
  ⚠️ `Session(&gorm.Session{})` **不会**丢掉对象上已有的条件，只保证对象本身不被改坏。
- **嵌套 `Transaction` = SAVEPOINT**，内层返回 `nil` 不代表落库，外层回滚时照样没（实测日志只有 `SAVEPOINT`，没有第二个 `BEGIN`）。
- **GORM 不打印 `BEGIN`/`COMMIT`/`ROLLBACK`**（源码无 trace 点），只有走 `Exec` 的 `SAVEPOINT` 会打印。
  → 不能靠日志判断有没有事务；要用连接 ID。

## 修正的三处错误（实测推翻）

| 位置 | 原来写的（错） | 实测事实 |
|---|---|---|
| 第 6 章 Map 创建 | 「struct 会把 `Age:0` 跳过，所以 INSERT 里没 age 列」 | **无 `default` tag 的字段零值照写**：`(name,count) VALUES ('a',0)` |
| 8.2 基础用法 | 「GORM 本身不会在 Go 侧填入默认值」 | **就在 Go 侧填**：`('anon',18,18)`，而且还会 `field.Set` **回写结构体**（`Create` 后 `d.Name == "anon"`） |
| 8.2 零值陷阱表 | 「`db.Select("Age")` 能强制插入 0」 | **Select 救不了**，零值仍被默认值替换 |

**正确规则**：零值被替换**只发生在带 `default` tag 的字段上**。
判据 `field.DefaultValueInterface != nil`（`schema/field.go`：`default` 值含括号的 DB 函数 / `null` / 空 → 不解析 → 零值时该列从 INSERT 省略交给数据库）。
另外实测：**map 创建完全绕过 `default` tag**（`(age,name) VALUES (0,'')`，struct 同样输入得到 `('anon',18,18)`）。

关键机制（源码 + 实测双证）：
- **查询回调链无事务**：只有 `gorm:query→gorm:preload→gorm:after_query`（callbacks.go:51-54），
  与写操作（含 begin/commit）对比是理解查询的第一前提。
- First/Take/Last 是 Find 变体（finisher_api.go:130-171）：First=Limit(1)+Order(PK ASC)、
  Take=Limit(1)、Last=Limit(1)+Order(PK DESC)，三者都设 `RaiseErrorOnNotFound=true`。
- ErrRecordNotFound 产生于 scan.go:366：`RowsAffected==0 && RaiseErrorOnNotFound && err==nil`。

- **意外发现**：复用目标变量会带主键残留（First 回写 id 后，下次 Take 自动带 WHERE id=1，场景 1b）。

## 晚间追加 · 更新 Update 文档

用户要求按同一套流程处理 update.html。产出：

关键机制（源码 + 实测双证）：
- **更新回调链**（callbacks.go:66-75）含 begin/commit（写操作默认事务）；钩子顺序
  `BeforeSave→BeforeUpdate→UPDATE→AfterUpdate→AfterSave`（后钩子 Update 在前，与 Create 对称）。
- **Save 是 upsert**（finisher_api.go:85-127 三分支）：无主键→Create；有主键→`Select("*")` 全字段 Update（零值也写）；
  Update 0 行→回退 `SkipHooks`+`OnConflict UpdateAll` 的 Create。Save 与 Model 混用是未定义行为；Generics API 移除了 Save。
- **`Select("*")` 连主键/created_at/deleted_at 都写进 SET**：新构造零值 struct 会把 created_at 写成
  '0000-00-00'、id 写成 0，MySQL 报 Error 1292（实测场景 8 铁证）。Save 安全前提是传"查出来的完整对象"。
- **Updates(struct) 所有零值字段无条件跳过**（false/0 都跳过），map 全保留 —— 与 Create 的 default-tag 规则是两码事。
  批量"置 false/清零"必须用 map 或 Select（场景 14：struct 的 Active:false 被静默跳过）。
- **RowsAffected 被 updated_at 污染**：Update 自动刷新 updated_at，业务值没变也计 1 行（场景 15：UpdateColumn=0 vs Update=1）。
- **UpdateColumn = SkipHooks=true**（finisher_api.go:426-438）→ 不触发钩子 + 不刷新 updated_at。
- **无条件更新保护** checkMissingWhereConditions（helper.go:109-123）：软删除模型的 `deleted_at IS NULL` 不算用户条件，仍拦。
- MySQL 子查询更新不能引用正在更新的表（跨表可以、同表套派生表）。
